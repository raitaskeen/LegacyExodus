## #198 counterexample: stale snapshot reused by a different analyzer build

**Invariant claimed:** a snapshot is reused only if it "was produced by the running analyzer build".

**Mechanism.** `getAnalyzerFingerprint()` (`src/runtime/analyzer-fingerprint.ts:50`) is lazy and cached per process. On a run with no valid signed snapshot for this location, its first call is at projection time (`file-discovery-projection.ts:182`), after the whole analysis. That covers first analysis, `--refresh`, every project's first run after upgrading (all old snapshots are unsigned), and any MAC or path failure; the validator only computes the fingerprint after the MAC passes (`discovery-validator.ts:430`). So the snapshot gets the identity of the source on disk at the end of the run, not of the code that ran.

**Reproduction A (deterministic, in-process).** Scratch clone at 140ec83, probe `probe/p1-edit-after-load.ts`.
1. Project: `handler.js` = `function handler(req, res) { const value = req.headers; res.send(value); }`.
2. P1 creates the engine (old code loaded: `sources` has no `req.headers`, fingerprint `8676af…`), edits `src/flow/data-flow-builder.ts:40` to add `"req.headers"`, then runs a default analyze (no `.discovery` yet).
   Result: 0 taint flows, and the manifest is signed with fingerprint `3306505…` (the edited source). `snapshotClaimsLoadedBuild: false`.
3. P2 runs a new process with the edited analyzer (`3306505…`), default analyze. **Expected:** not reused, 1 flow. **Actual:** `isReused: true`, 0 flows served.
4. P3: the same build with `--refresh` gives 1 flow.

**Reproduction B (real CLI, realistic timing).** Probe `probe/cli-race.ts`, on an express copy plus one `req.headers` handler.
- `bun run src/cli/index.ts analyze <p> --refresh` ran as a child process for 12.2 s; the analyzer source was edited 1.5 s in.
- The snapshot holds 16 flows and claims fingerprint `3306505…`.
- The next default `analyze` with the edited analyzer printed **`Snapshot reused: yes, from analysis run c9eeba21…`** and served 16 flows; `--refresh` gives 17.
- Logs: `logs/probe-toctou-race1.log`, `logs/probe-toctou-cli2.log`.

**Why this invalidates the candidate.** It is exactly F-001's harm: an engine change is silently skipped for a previously analyzed repository, while the system asserts it checked analyzer identity. The control (edit before the run) behaves correctly, which isolates the defect to when the fingerprint is captured.

**Path A fix.**
- Capture the fingerprint eagerly at composition or process start, before any analysis, and use that value for both validation and signing.
- At signing, recompute it; if the on-disk identity changed during the run, write the manifest unsigned.
- Regression test via the existing `EngineCompositionOptions.analyzerFingerprint` seam: return "A" until the test flips it to "B" after `initialize()` and before `execute`. Assert the manifest says "A" (or is unsigned). It fails today.

## #199 counterexample: stale projection reused in a normal `bun test` run

**Claim** (helper comment, `test-fidelity-helpers.ts:130`): capturing the fingerprint at helper load "keeps a record describing the code that produced the projection even if the source is edited mid-run". The PR's contract is to reuse a projection only when the current analyzer produced it.

**Mechanism.** `bun test` runs all files in one process with a shared module registry. The engine is first loaded by earlier test files; the helper's `loadedAnalyzerFingerprint` is read when the helper module is first evaluated, much later.

- Measured in an instrumented full run (scratch): engine composition evaluated at **0.18 s**, fidelity helper at **32.01 s**. The window is about 32 s, not the "ms window" in the author's handoff.
- That instrumented run also had 4 unrelated failures (SQLite atomicity and post-commit diagnostics). The clean gate run at the same SHA passed, so they are not counted.

**Reproduction.** Scratch clone at 521b86e; probe tests `zz-race-parked/zz-race/{a,b,c}.test.ts`.
1. Process 1: `bun test a.test.ts b.test.ts`. File A imports `@runtime/composition/services`, then edits `data-flow-builder.ts` to add `"req.headers"`. File B imports the helper and calls `ensureDiscoveryProjections(project)`.
   Result: projection has 0 taint flows (old code ran), record fingerprint `1f43d05c…` (edited source).
2. Process 2 (edited analyzer): `ensureDiscoveryProjections(project)`. **Expected:** regenerate. **Actual:** `reused=true`, 0 flows served. Forced regeneration by this analyzer gives 1 flow.
3. Log: `logs/probe199-registry.log`.

**Path A fix.** Capture the identity in a test preload (bunfig `[test] preload`) before any test file loads the engine. Before writing a record, check that the on-disk fingerprint still equals the captured one; otherwise write no record.

**Test quality.**
- The new cases discriminate the main logic: RED failures are at the intended assertions.
- Load-time capture, the failure path and Bun-version input are untested (the author says so for capture and Bun version).
- Case 3's `execSync` mock no longer affects the helper, so it duplicates case 1.
- After #198 merges, case 12 would pass even without `refresh: true`, because the MAC rejects the tampered manifest.
