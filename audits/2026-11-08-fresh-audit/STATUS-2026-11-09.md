real code stay unresolved, by design), multi-framework (Express only), multi-language, or externally validated.

## 5. Accuracy: what is and is not measured

| Measure | Result | What it means |
|---|---|---|
| Conformance corpus (`bun run benchmarks/cli.ts accuracy`) | 189/189 planted facts, 37/37 negative controls, 0 known gaps | Every language feature and trap we have written down is handled. The corpus is ours, so 100% is a floor for regressions, not a claim about the world |
| Ground truth, Express and Fastify (Track 3) | 296 hand-verified facts, 0 missed | Sample-based (25 files each); whole-repository safety is not established |
| Taint probes from the 8 Nov audit | All runtime-proven flows found | The flows are proven by running the programs |
| Call resolution on real code (all calls / outside test files) | Ghost 15.9% / ~20%; Fastify 7.4%; Express 9.0%; engine source 20.5% | **Low by design**: most calls go to packages, built-ins, test frameworks, or need types. What is RESOLVED is proven |

Why calls stay unresolved, on Ghost (share of unresolved): third-party packages 24%, calls on call results 19%,
methods on local objects 16%, Node built-ins 10%, JavaScript globals 9%, browser and test-runner globals 8%; 77%
of all unresolved calls are in test files. Raising resolution further needs **types** (what object a value holds),
which belongs to the Semantic IR, not to more name rules.

**Not measured yet, and the main credibility gap:** a head-to-head on public benchmarks (OWASP Benchmark,
a SecBench.js-style set) against Semgrep and CodeQL. That is also the strongest basis for the research paper.
